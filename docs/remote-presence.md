# AKASHI remote presence (Spatial Lab V1.5)

Remote presence lets another device — an iPhone, a Mac, another laptop — join
AKASHI as a **scoped, authenticated part of a distributed body**: it advertises
what it can provide (camera, microphone, touch, display, approvals…), it sends
input and requests, and it shows Core's authoritative state. Spatial Lab is the
first consumer; the layer itself (`backend/app/remote`, `frontend/src/lib/remote`)
is domain-independent.

Measured status and local tests: [acceptance contract](acceptance/remote-spatial-presence-v1-5.md).

```text
REMOTE DEVICE (iPhone / Mac / laptop)                       AKASHI CORE (primary PC)
┌───────────────────────────────────┐                      ┌──────────────────────────────────────────┐
│ camera → MediaPipe (on device)    │                      │ RemoteHub: sessions · scopes · order ·   │
│ touch / pointer → gesture engine  │  akashi.remote/1     │   dedupe · rate · staleness · audit      │
│ speech → transcript (on device)   │ ───────────────────► │   ├─ Spatial bridge → SpatialLabService │
│ UI actions                        │  WebSocket or        │   │     (one command path, history)      │
│ RemoteSessionClient (resilient)   │  HTTP long-poll      │   ├─ ApprovalCenter (spatial/tasks/…)    │
│ RemoteSpatial (replica by rev.)   │ ◄─────────────────── │   ├─ RemoteVoice → Spatial / chat        │
│ renderer (same three.js view)     │  events · previews · │   └─ CapabilityRegistry                  │
└───────────────────────────────────┘  leases · approvals  └──────────────────────────────────────────┘
```

## 1. Principles

* **Core is authoritative** for scene state, object identity, transforms, FORM
  version identity, validation, history, undo/redo, replay, permissions and
  approval state. A device never sends state — only requests, input and
  sensor-derived data. Its view is a replica that Core can always replace.
* **Sensors stay on the device.** Camera frames and microphone audio are
  processed on the device. Core receives hand anchors, gesture intents,
  transcripts and commands. No raw-video or audio channel exists in V1.5.
* **Least privilege.** A device holds only the scopes the owner granted. No
  scope can grant computer control (Agent actions, browser, files, autonomy).
* **One history.** Remote actions are ordinary Spatial requests with remote
  provenance, recorded in the same hash-chained action history.

## 2. Device identity and capabilities

**Identity** lives in the existing device registry (`app/devices/store.py`; no
second registry). A new role `presence` sits next to the Windows Agent role:

| Field | Meaning |
| --- | --- |
| `role: "presence"` | Remote presence node; can never be the target of an Agent action (`queue_action` refuses it, Agent endpoints reject it). |
| `grants` | Owner-chosen scopes (§4). Changed only by the owner. |
| `credential: "key"` + `public_key` | P-256 public JWK; the private key was generated non-extractable on the device. |
| `credential: "secret"` | Fallback for insecure browser contexts only; salted PBKDF2 hash, labelled weaker in the UI. |

**Capabilities** are separate, per session and dynamic (`app/remote/capabilities.py`):
`camera, microphone, touch, pointer, keyboard, hand_tracking, gesture,
orientation, display, speech_output, voice_input, notifications,
approval_surface`, each `available | active | unavailable | denied` with small
details (e.g. `voice_input.engine`, `camera.processing: on-device`). Devices
update them during a session (`capabilities.update`), e.g. camera → `denied`
after a refused permission prompt, `active` while hand tracking runs.

"Which connected device can provide X?" — `CapabilityRegistry.providers(X)`
(live, non-stale sessions only), exposed as `GET /remote/providers`, the
`remote.devices` tool and a live action ("Which device can provide a camera?",
"Hangi cihazlar bağlı?").

## 3. Pairing and authentication

1. Owner (API token) creates a one-time code with chosen scopes:
   `POST /remote/pairing-codes {preset|scopes}` (10 chars, ≥ 60 s TTL, single use,
   pairing attempts rate-limited). A presence code cannot pair an Agent and vice versa.
2. Device: `POST /remote/pair {code, name, device_type, public_key}`. The key is
   generated by WebCrypto (`extractable: false`) and stored as a `CryptoKey` in
   IndexedDB; only the public JWK leaves the device. Private-key members are refused.
3. Every session: `POST /remote/challenge {device_id}` → single-use nonce (60 s,
   bound to the device) → device signs
   `akashi.remote.session/1\n<device>\n<nonce>\n<sorted scopes|*>` (ECDSA P-256,
   P1363) → `POST /remote/sessions` → short-lived session credential (random
   256-bit, stored as SHA-256), scopes = requested ∩ granted.
   *Replay protection:* the nonce is consumed on first use (even a failed one);
   the requested scopes are inside the signature.
4. Realtime transport authenticates with the session credential — in the first
   WebSocket frame (never in a URL) or `Authorization` on the HTTP transport. The
   owner's own session (desktop/web) is opened with the API token
   (`POST /remote/owner-sessions`); on the desktop it rides the IPC bridge, so the
   token never reaches the renderer.

Handshakes are rate-limited per device and globally. Unknown, revoked or
mis-signed devices are refused and the refusal is audited (rate-limited).

## 4. Scopes (permissions)

| Scope | Allows |
| --- | --- |
| `spatial.view` | See the scene, history, leases, roster; fetch scene assets. |
| `spatial.control` | Change the scene (requires view). |
| `spatial.presence` | Share hand anchors/cursors (requires view). |
| `voice.spatial` | Voice/text scene instructions (requires view + control). |
| `assistant.chat` | Converse with AKASHI; live actions limited to `REMOTE_LIVE_ACTIONS` (scene + device info). |
| `approvals.spatial` | Decide Spatial Lab confirmations. |
| `approvals.general` | Decide all AKASHI approvals (tasks, autonomy). Explicit opt-in. |

Presets: `spatial-remote` (view, control, presence, voice.spatial,
approvals.spatial), `spatial-viewer`, `approver`. Scopes are checked on **every
message** against the session's current scopes. Changing a device's grants or
revoking it takes effect for live sessions before the owner's request returns
(the hub re-reads the registry on every change), releasing leases a device no
longer may hold and closing its sockets on revocation (WebSocket close 4403).

## 5. Protocol `akashi.remote/1`

Client → Core: `{v:1, id, seq, t, kind, body}`; Core → client: pushed
`{v:1, sseq, kind, body}` or replies `{v:1, kind:"ack"|"error", re, seq, body}`.
Contract: `shared/contracts/remote/protocol.json` (generated by
`python -m app.remote.contract`, checked by both test suites).

| Rule | Effect |
| --- | --- |
| `id` (idempotency key) | A repeated id returns the cached reply; it is never applied twice. |
| `seq` reliable kinds | `seq ≤ last processed` → `out_of_order`, never applied. |
| `seq` realtime kinds | Older than the newest of the kind → silently superseded. |
| `t` (device clock) | Only relative delay: `ClockEstimator` learns the offset from the least-delayed message; realtime input older than its budget (preview 400 ms, presence 1 s, renew 1.5 s) is dropped. A sustained shift (sleep/clock jump) re-baselines. |
| Rate classes | reliable 20/s (burst 40), realtime 90/s (120), voice 1/s (3), approvals 5/s; refusals are retryable and do not consume `seq`. |
| Size | 64 KiB per message, 32 per HTTP batch. |
| `sseq` | Monotonic, not contiguous (superseded lossy messages are dropped). Used only to resume delivery, never to infer state. |

**Transports.** WebSocket (`/remote/ws`) and HTTP (`POST …/messages`, long-poll
`GET …/poll?after=`). The client tries WebSocket, falls back to HTTP after two
failures; the desktop always uses HTTP through IPC (CSP `connect-src 'self'`).
WebSocket connections from origins outside `AKASHI_CORS_ORIGINS` are refused.

**Reachability is provider-independent.** Core only needs to be reachable over
HTTPS from the device (LAN reverse proxy, VPN, any tunnel). Optional
`AKASHI_REMOTE_ENDPOINTS` lists addresses advertised to paired devices. No
commercial tunnel is required or built in.

## 6. Session lifecycle and failure behaviour

| Situation | Behaviour |
| --- | --- |
| No traffic for 12 s | Session `stale`; its leases and hand anchors are released; viewers drop its previews (objects snap to the last committed transform). |
| No traffic for 90 s, or 12 h lifetime | Session closed; device performs a new handshake with its key (automatic). |
| Short disconnect | Client reconnects with backoff + jitter, resumes after the last `sseq`; unanswered requests are resent unchanged (same id/seq). |
| Sleep / wake, network change | `online`/`visibilitychange`/`pageshow` trigger an immediate attempt; silence beyond `stale_after` forces a reconnect even if the socket never reported closing. |
| Session replaced (expiry, Core restart) | Unanswered requests fail as `outcome_unknown` (never resent: the new session cannot de-duplicate). The scene is re-read. |
| Core restart | Sessions are not persisted; devices re-handshake and re-sync by revision + digest (events if their copy is provably identical, else a snapshot). |
| Duplicate command | Answered from cache, applied once. |
| Out-of-order / stale transform | Rejected (`out_of_order`, `stale_state`); the scene never moves backward. |
| Unknown device / bad signature / expired nonce | `401`, audited. |
| Revoked | Live sockets get `revoked`, close 4403; device shows "revoked"; no new handshake possible. |
| Scope removed | Immediate; e.g. losing `spatial.control` releases held objects. |
| Backlog (client not reading) | Outbox dropped, `resync_required` sent. |

## 7. Spatial Lab integration

* **Provenance.** `Origin.kind = "remote"` with `origin.remote = {device_id,
  device_name, device_type, session, session_kind, modality (gesture | touch |
  pointer | language | voice | ui), message_id, seq, sent_at_ms, received_at,
  transport}` — set by Core, never accepted from a caller (`/spatial` HTTP
  rejects `origin_reserved`). Confirmations add `origin.approval` (who approved,
  from which device/session).
* **Why did this move?** `GET /spatial/sessions/{id}/objects/{obj}/provenance`,
  hub kind `spatial.provenance`, and language ("why did it move?", "bunu kim
  taşıdı?") → "Last change to Box was #12 (Transformed Box) at 14:02:11: Remote
  touch from Metin's iPhone (session rs-…)". The desktop inspector shows it.
* **Stale protection.** Requests carry `base_revision`; if a target object was
  changed after it (selection/view changes excepted), Core answers
  `stale_state` with who changed it. Undo/redo require the current revision.
* **Leases are owner-bound.** Only the holding session can renew, preview,
  commit or end its lease (the local owner keeps authority); a departing or
  demoted device's leases are released at once.
* **Live previews.** The holder streams `spatial.preview` (~30 Hz, lossy,
  coalesced per lease, validated against scene limits, never recorded); viewers
  see "held by iPhone" and the object moving; the single committed transform at
  release is the only history entry, published *before* the preview ends.
* **Presence per device.** Hand anchors are stored per source; "move it to my
  right hand" uses the anchors of the device that spoke.
* **Sync.** Events fan out in strict history order with their patches; clients
  apply by revision and re-sync on any gap or inconsistency.
* **Same input stack.** Touch becomes pinching hands in the existing gesture
  pipeline (one finger drag, tap select, two fingers scale/turn); camera hands
  run MediaPipe on the device; both drive the existing gesture controller
  through a remote port.

## 8. Approvals

`app/approvals/center.py` reads pending approvals from their owners — Spatial
confirmations (`spatial`), task-engine approvals and autonomy approvals
(`general`) — and routes decisions back. Items carry *what* (title, action),
*why* (reason) and *who asked*. Decisions need the matching scope, are recorded
in the remote audit trail with device and session, are idempotent
(`already_decided` with the recorded decision) and are pushed to approver
sessions when the pending set changes. Deciding is deliberately **not** a tool:
a person decides on an authorized surface.

## 9. Voice

The device turns speech into text on the device (`voice_input.engine`:
`native` via the Capacitor app, or `web-speech`, labelled as possibly using the
browser vendor's cloud). It sends `voice.utterance {text, language, engine}`.
Core routes it through existing paths — Spatial interpreter (with
`voice.spatial`) or AKASHI chat (with `assistant.chat`, live actions limited to
scene actions) — and returns the reply, spoken on the device. The lifecycle is
recorded in the existing `VoiceSessionManager`. Typed text always works; no
cloud speech service is required by Core.

## 10. Audit

`app/remote/audit.py` reuses `app.history.ActionLog` (hash-chained, fsync'd,
segmented): code creation, pairing, session open/close (with reason),
refusals, forbidden messages, grant changes, revocations and approval
decisions. A tampered log is never repaired: pairing, sessions and approval
decisions are refused until the owner moves it aside. `POST /remote/audit/verify`
re-reads the file and checks the chain.

## 11. API summary

| Audience | Endpoints |
| --- | --- |
| Owner (API token) | `GET /remote/status`, `GET /remote/catalog`, `POST /remote/pairing-codes`, `GET /remote/devices`, `PATCH/DELETE /remote/devices/{id}`, `GET /remote/providers?capability=`, `GET/POST /remote/approvals[/{id}]`, `GET /remote/audit`, `POST /remote/audit/verify`, `POST /remote/owner-sessions` |
| Device | `POST /remote/pair`, `POST /remote/challenge`, `POST /remote/sessions` |
| Session | `WS /remote/ws`, `POST /remote/sessions/{id}/messages`, `GET …/poll`, `DELETE …`, `GET …/assets/{asset}` |

Message kinds: `ping`, `capabilities.update`, `session.close`,
`devices.providers` (owner), `spatial.{sessions,subscribe,command,interpret,confirm,
lease.begin,lease.renew,lease.end,preview,presence,provenance,events}`,
`approvals.list`, `approval.decide`, `voice.utterance`, `voice.state`.

## 12. Product surfaces

* **Remote client** `/remote` (browser or the Capacitor app): pairing, connection
  state, the scene (same renderer), touch / pointer / hands, selected-object
  actions, text and voice, approvals, history with provenance, devices and
  permissions, debug metrics; explicit revoked/unpaired screens.
* **Owner** (Spatial Lab → *Devices*): invite with permissions, live devices and
  capabilities, permission toggles (immediate), revoke, approvals, audit
  verification; "held by" labels, remote hand anchors, provenance in the inspector.

## 13. Reuse beyond Spatial Lab

A new consumer registers kinds on the hub
(`hub.register(kind, handler, delivery=…, any_of=(scopes…))`), subscribes
sessions to channels and listens to lifecycle events (`closed`, `stale`,
`scopes`) to release what a device held. New scopes go in `scopes.py` (never a
computer-control scope without a separate, explicit design), new capabilities in
`capabilities.py`. The frontend reuses `RemoteSessionClient` + a transport and
writes a small port like `RemoteSpatial`.

## 14. Not in V1.5

Raw video/audio streaming (would be a separate, explicitly granted capability),
QR pairing, push notifications to sleeping devices, multiple simultaneous
owners, session persistence across Core restarts (deliberately not: devices
re-authenticate), Core-initiated sensor activation, distributed execution on
remote devices.

## 15. Running and testing

```bash
# Core reachable from the device over HTTPS (any reverse proxy / VPN / tunnel):
AKASHI_REMOTE_ENDPOINTS=https://akashi.lan:8443          # optional, advertised to devices
AKASHI_CORS_ORIGINS=...,https://<origin serving the UI>  # for browser clients
# Backend tests (hub, Spatial bridge, approvals/voice, API/WS, network simulation, contract)
cd backend && .venv/bin/python -m unittest tests.test_remote_hub tests.test_remote_spatial \
  tests.test_remote_core tests.test_remote_api tests.test_remote_network tests.test_remote_contract
.venv/bin/python -m app.remote.contract        # contract artifacts current?
# Frontend
cd frontend && npm run test:api                # includes tests/remote-client.test.mjs
npm run build && npm run test:spatial          # includes tests/spatial-e2e/remote-presence.spec.ts
```
